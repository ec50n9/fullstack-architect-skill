# Feature & Refactor Workflow

当加载本文件时，严格按 Phase 0 到 Phase 4 顺序执行：

## Phase 0: 接入即演进（第一性原理纪律）

已有功能和新功能都不是既成事实：已有功能开发时未预见新功能，新功能开发时未预见未来所有功能。接入时对两者都可质疑，依次执行：

1. **质疑前提**：拟议方案要解决的问题真实存在吗？
2. **溯源动机**：用 `git log -S` / 规划文档搞清原设计当时为什么合理。
3. **找更优设计**：优先在基建一处收敛，拒绝各页面抄写变通。（MVP 验证阶段允许登记 `DEBT.md` 后按现状执行。）
4. **确无更优**才按现状执行。

**判定信号**：一条既有规范若迫使每个新功能做主观判断题，优先怀疑基建缺口，而非照抄。

## Phase 1: Inventory & Decision Tree

静默读取项目上下文（包括 `package.json`/`go.mod` 等依赖文件，以及 `core/`, `utils/`, `components/` 核心目录）。
若项目是 TypeScript/JavaScript 全栈项目，同时读取 [typescript-fullstack-constraints.md](typescript-fullstack-constraints.md)，并将其作为技术决策的强制约束。
严格按照以下优先级制定技术决策：

- **P1[复用最高级]**: 直接复用现有第三方库的 API。
- **P2 [内部调用]**: 调用项目中现存的公共组件/服务/函数。
- **P3 [引入新库]**: 仅在需求复杂且边界情况多时，引入符合最新生态的轻量级库。
- **P4 [纯手写]**: 仅在引入库会导致包体积无意义膨胀且业务闭环时，自行封装。

## Phase 2: Architecture Alignment

评估代码落盘位置：

- **跨模块复用**：立即提取到全局公共层（`utils/`, `services/`, `hooks/` 等）。
- **单模块独享**：严格遵循“就近原则 (Colocation)”，防止全局空间污染。
- **范式冲突**：检查新代码写法是否与旧代码冲突。若冲突，将重构旧代码拉齐标准纳入计划。（MVP 验证阶段允许登记 `DEBT.md` 暂缓拉齐。）
- **全栈边界**：前端/后端/共享包/API DTO/数据库实体/核心业务层必须满足 TypeScript 全栈工程约束；发现边界破坏时，将边界修复纳入计划。

## Phase 3: Proposal (必须暂停)

**【禁止输出代码】** 输出 Markdown 预案并暂停：

1. **决策依据**：选择 P1~P4 中哪一种？复用什么代码或引入什么库？
2. **架构落脚点**：代码将存放在哪些目录层级？
3. **爆炸半径**：需要激进重构哪些旧代码？
4. **工程约束校验**：说明前后端隔离、DTO/Mapper、运行时校验、SSOT、Result 错误模型、环境变量校验是否受影响，以及对应处理方案。
5. **结尾附加提示符**：
   `🟢 预案已生成。请回复：[1] 执行该方案 [2] 调整方案 [3] 补充缺失的上下文信息。`

## Phase 4: Execution

仅当用户回复 `[1]` 时继续：

1. 先输出：公共层提取、底层重构、旧代码对齐代码。
2. 后输出：具体的新业务特性代码，确保高内聚低耦合。
