# Bug-Fixing Workflow

当加载本文件时，严禁“头痛医头”给临时补丁，必须通过彻底重构解决问题：

## Step 1: Trace

- **现象验证**：推导该 Bug 在当前代码中是否必然存在。如果不复现，告知用户并停止。
- **全链路追踪**：还原完整调用栈（例：UI 交互 -> 状态流转 -> 接口组装 -> 后端路由 -> Service -> DB 事务），定位真实触发点。

## Step 2: Intent Check (关键节点)

- 判断该现象是否属于系统原有的“合理设计 (By Design)”。
- **【交互中断】**：若遇到上下文缺失或设计意图存在歧义，**立即暂停并提问**，严禁自行脑补猜测。

## Step 3: Deep Analysis

- 当确认为真实 Bug 后，沿调用链路排查同维度的所有隐患（如：并发竞态条件、数据一致性破坏、异常捕获断层）。
- **Zero-Baggage 原则**：寻找最底层的脆弱点进行修复，绝不考虑向后兼容。

## Step 4: Proposal (必须暂停)

**【禁止输出补丁代码】** 输出 Markdown 预案并暂停：

1. **真实根因**：全链路分析下的最底层缺陷是什么？
2. **底层重构方案**：给出能一劳永逸解决该类问题的重构方案（如：重写数据流、修改数据库关联、提取容错中间件）。
3. **爆炸半径**：该底层修复波及的关联模块。
4. **结尾附加提示符**：
   `🔴 根因修复预案已生成。请回复：[1] 同意进行底层重构修复 [2] 修改修复策略 [3] 解答上述甄别阶段的疑问。`

## Step 5: Execution

仅当用户回复 `[1]` 时继续：
输出彻底重构与修复后的完整代码，确保该底层隐患永久根除。
